# 防火检查站 × 物资预警：状态一致性改造设计

## 1. 背景与问题定位

防火检查站的「状态」分散在三个界面读取，但旧实现各自写各自的字段、没有统一权威源，导致互相冲突：

| 界面 | 读取位置（旧实现） | 问题 |
| --- | --- | --- |
| 站点列表 | `checkpoint` 行的 `status` | 被通用动作 `runAction` 盲写，与最新现场检查脱节 |
| 通行详情 | `checkpoint` 行 + `duty` 排班行 | 升级检查后仍显示可换岗；班次引用的站点状态是旧值 |
| 物资预警 | `supply` 行的 `status` | 是写死的存量字段，检查/物资变化后不重算，残留旧值 |

四个具体故障的根因：

1. **升级检查后旧站点仍能安排换岗**：`runAction` 不做任何前置状态校验，只判断「目标状态与当前是否相同」。站点已经是「升级检查」，点「安排换岗」（目标=正常检查）仍会成功，现场检查结果被覆盖。
2. **收缴火种数重复显示**：站点行里有一份「收缴火种数」存量字段，现场检查又产生一份火种数据，两处相加/并列，导致一个火种被算两次。
3. **物资预警残留旧值**：`supply.status` 是静态写库字段，实际储备量变化后没有任何环节重算预警；「另一个模块」（物资储备页）读到的也是这同一份旧值。
4. **并发换岗产生多个结果**：动作每次独立读—改—写整个 `checkpoint` 表，无版本号/锁，两次并发提交都会成功，后写覆盖先写。

## 2. 权威与冲突仲裁口径

- **站点状态以现场检查为唯一权威源**：站点当前状态由该站点**最新一条有效现场检查记录（checkpointInspection）**与显式管理态共同裁决。站点行只做投影，不再由通用动作直接改写。
- **冲突仲裁规则**：同一站点出现多条相互冲突的检查结论时，按 `检查时间` 取最新；`检查时间` 相同则取 `检查记录ID` 更大（后到）的一条。被仲裁下去的旧检查记录保留为历史，不删除。
  - 最新现场结论是**升级检查** → 以现场为准，压过等待换岗/临时关闭等一切管理态；
  - 最新现场结论是**正常检查** → 只负责解除「升级检查」；在途的「等待换岗 / 临时关闭」是显式管理动作，分别由完成交接 / 重新开放结束，不被正常检查自动打断（否则换班会在提交瞬间被投影打回）。
- **升级检查锁定换岗**：站点处于「升级检查」时，安排换岗一律拒绝（返回业务错误，不建班次、不动站点、不动预警）。只有「解除升级」或升级检查结束回到「正常检查」后，才允许再排班。
- **历史班次兼容**：已存在的历史班次不动、不回写新状态，其站点状态以**该班次的原检查时间**为准 —— 班次保存「原检查时间快照（sourceCheckedAt）」和当时的站点状态快照（sourceStationStatus），任何展示冲突都按「时间点回放」解释，而不是用站点现值覆盖历史。

## 3. 状态经过哪些环节（站点链路）

现场检查驱动的站点状态机（每个迁移都有守卫，不再允许任意跳转）：

```
            升级检查(现场)                 解除升级
 正常检查 ───────────────▶ 升级检查 ───────────────▶ 正常检查
   │  ▲                      │ 现场复查为正常           ▲
   │  │ 重新开放/            │（生成更晚的正常检查）     │
   │  │ 换班交接完成          ▼                         │
   │  └──────────────  （按最新检查自动回到正常检查）    │
   │                                                完成交接
   │ 关闭站点                    安排换岗                  │
   ├──────────────▶ 临时关闭                   等待换岗 ──┘
   └──────────────▶ 等待换岗（仅正常检查可进入）
```

每个动作经过的环节（统一编排，一个事务内完成）：

1. **守卫（Guard）**：校验当前站点状态是否允许该动作；校验乐观锁版本号（并发仲裁）。
2. **现场检查落账**：升级检查/现场复查先写一条 `checkpointInspection`（含检查时间、火种数、车辆数、现场状态）。
3. **站点投影更新**：用最新有效检查记录重算站点 `status / pending / 收缴火种数投影 / version+1`。
4. **班次落账**（仅安排换岗/完成交接）：写或更新 `checkpointShift`，记录原检查时间快照。
5. **物资预警重算**：全量重算 `supplyWarning` 投影并随同一事务落库。
6. **同次提交**：站点、检查/班次记录、预警三部分在一个 Unit of Work 里一次写入；任一步抛错则整体回滚，内存与 localStorage 都不留半成品。

## 4. 物资链路与预警重算口径

- 物资权威数据是 `supply` 行的 `实际储备量 / 预警储备量`；`supplyWarning` 是**派生投影**，永远由权威数据重算得到，不允许手工残留。
- 重算在每次检查站事务提交时触发，重算结果与站点/记录**同次落库**；检查站页与物资储备页读的是**同一份投影**，因此两模块清单天然同步，不再各存一份。

预警级别补值口径（按顺序判定，先命中先返回）：

1. 物资 `物资状态` 被人工标记为「已过期」→ `已过期`（过期优先于数量）。
2. 实际储备量 ≤ 0 或实际 ≤ 预警储备量 × 50% → **需补充（红）**。
3. 实际 ≤ 预警储备量 → **偏低（黄）**。
4. 其余 → **充足**。

补值细则：

- 数量字段无法解析为数字时一律按 `0` 处理，不抛错、不阻断落库。
- 关联站点：站点「升级检查」时，其同林场（`储备林场` 与站点 `所属林场` 相同）的未达标物资额外打 `关注=true`，供检查站页置顶；但级别仍只由物资数量/过期口径决定，不凭空改库存。
- 预警与物资按 `物资编号` 一一对应；物资被删除/重置后，其预警在下次重算时消失，不残留。

## 5. 补值口径（缺失/历史脏数据）

### 5.1 现场检查记录补值

- `检查时间`：未提交时取服务端当前时间；格式统一 `YYYY-MM-DD HH:mm`。
- `值守人员 / 所属林场 / 站点位置`：从站点主数据带入（现场表单不重复填，避免两处不一致）。
- `通行车辆数 / 收缴火种数`：现场报数；缺省或非数字补 `0`，禁止用站点旧累计值倒填。
- `现场状态`：默认「升级检查」；现场复查提交「正常检查」。
- `检查项目`：缺省补「常规检查」。
- 每条检查记录不可修改，冲突只靠「再提交一条更晚的记录」覆盖裁决，满足以现场为准、且可审计。

### 5.2 站点统计补值

- 列表「收缴火种数」列与顶部统计**只取现场检查记录的火种数**：
  - 站点现值 = 该站点**最新一条**有效检查记录的火种数（当前口径，不累计历史，避免重复）。
  - 顶部「收缴火种数」= 各站点最新检查记录火种数之和（每个站点只算一条，杜绝重复）。
- 站点行旧的存量「收缴火种数 / 通行车辆数」字段降级为迁移兜底：无任何检查记录时按 `0` 展示，不再参与合计。

### 5.3 班次补值与历史兼容

- 新建班次：`接班人员` 缺省补「待指派」；`值勤时段` 缺省补「待排」；`原检查时间` 固定取安排换岗**那一刻站点最新检查记录的检查时间**（不是排班时间），并冻结当时站点状态快照。
- 历史班次（旧数据迁移）：若缺 `原检查时间`，回填为站点 `值班日期 00:00`；缺状态快照回填站点现值，并标 `snapshot=true` 表示「补值快照」。历史班次永不因站点后续变化而改写。

### 5.4 旧数据迁移（localStorage 已存在的 v1 数据）

- 首次进入时一次性迁移（按数据形状探测，幂等）：
  - `checkpoint` 行补 `version`（=0）、`所属林场`（缺省补「未归属林场」）。
  - 从站点存量字段补建一条基线现场检查记录（检查时间取 `值班日期 00:00`，火种/车辆缺省 0，标 `baseline=true`），保证「现场检查为权威源」对旧站点也成立。
  - 重建 `supplyWarning`，清掉与现状不符的残留旧值。

## 6. 并发与事务

- **乐观锁**：站点行带 `version`。安排换岗等动作必须携带读到的版本；提交时版本不一致即拒绝（提示「站点已被他人更新」），不覆盖。
- **同站排他**：同一站点「等待换岗」期间再次安排换岗直接拒绝 —— 并发两次换岗只有第一个成功，第二个拿到的已是新版本/非允许状态，只接受一个结果。
- **Unit of Work**：`commitAll(draft)` 一次性替换全部相关集合（checkpoint / checkpointInspection / checkpointShift / supplyWarning）。先在内存草稿上完成全部变更，全部成功才落 localStorage；中途异常不触碰缓存，等价于站点、记录、预警同次落库、失败一起退回。

## 7. 代码落点

- `src/data/local-store.ts`：新增 `commitAll` 事务写入口（多集合一次落库/回滚）。
- `src/domain/checkpoint.ts`（新增）：检查站领域 —— 状态机守卫、现场检查、班次、火种统计、乐观锁、物资预警重算、旧数据迁移与补值。
- `src/api/local-service.ts`：物资模块动作/重置后同事务重算预警；导出检查站领域读写接口。
- `src/views/checkpoint/index.vue`：列表按守卫出动作、补值弹窗（升级检查/安排换岗）、通行详情（现场检查记录）、同页物资预警清单；统计单一数据源。
- `src/views/supply/index.vue`：挂载同一份 `supplyWarning` 预警清单（另一模块同步）。
- `src/data/modules.ts`：checkpoint 状态集补齐「等待换岗」为独立流转态。
- `src/data/seed.ts`：新增检查记录、班次、物资预警种子，并放入一条与现状不符的旧预警用于验证重算清理。
